**Agentic 之道**

从 Vibe Coding 到 Context 复利

*一个人的 14 个月 Agentic 演化实录*

ChaoGeek · 2026

*亲手试过，才有资格说*

**序：一条推文引发的思考**

2026年4月，Y Combinator 掌门人 Garry Tan 在 X
上发了一条推文，标题叫「Thin Harness, Fat Skills」。他开源了自己的 AI
大脑------一个叫 GBrain 的系统，里面装着 10,000 个 Markdown 文件、3,000
个人物页面、13 年的日历数据、280 份会议记录。

这不是一个 demo。这是他每天在用的真实系统。他同时开源了
gstack------一套把 Claude Code 变成虚拟工程团队的 23
个专家角色。他声称过去 60 天产出了 60 万行生产代码，兼职，同时全职管理
YC。

但让我真正停下来思考的，不是这些数字。而是他的一句话：

> *The bottleneck is never the model\'s intelligence. The bottleneck is
> whether the model understands your schema.*

瓶颈从来不是模型的智能。瓶颈是模型是否理解你的数据。

这句话让我重新审视了过去 14 个月走过的路------从 Vibe Coding 到 Spec
Coding，从 OpenSpec 到
CodingSys，从精心设计的状态机到最后推翻一切回归极简。我意识到，所有这些探索最终收敛到了一个答案。

这个答案，我叫它 Agentic 之道。

**第一章：从 Vibe Coding 说起**

2025 年 2 月，Andrej Karpathy 提出了 Vibe
Coding------「完全屈服于氛围，拥抱指数级增长，忘记代码的存在」。你不审查代码，不理解实现，遇到错误就复制粘贴给
AI，通常就能修好。

这是一次解放。在 Karpathy 之前，大多数开发者对 AI
编程抱着怀疑态度------能写 Hello World 但写不了生产代码。Vibe Coding
打破了这个心理障碍。它教会所有人一件事：信任模型的智能。

我也信了。我试了，写了《Vibe Coding
之道》，在海南大学分享了这个理念。快速原型、概念验证、周末项目------Vibe
Coding 确实好使。

但问题很快出现了。

**Vibe Coding 的三个致命缺陷**

**第一，无状态。**每次对话从零开始。今天踩的坑，明天还会踩。这个项目的经验跟下个项目无关。你的
AI 像一个每天失忆的天才------聪明但不积累。

**第二，单向。**交互模式是「我说你做」。你描述需求，AI
生成代码。人是导演，AI
是演员。但最好的方案往往不是你一个人想出来的------它是碰撞出来的。单向交互丢掉了共创的可能性。

**第三，不可持续。**快速原型可以
vibe，生产系统不行。代码质量、安全漏洞、架构腐化------这些问题在 vibe
coding 模式下会指数级放大。一个人 vibe
出来的代码，三个月后连自己都维护不了。

这三个缺陷不是模型不够聪明造成的。换更强的模型也解决不了。它们是范式本身的局限。

**第二章：14 个月的演化**

从 Vibe Coding 到 Agentic 之道，不是一步到位的顿悟，而是 14
个月一步步试错走出来的。每一步都是因为上一步不够用。

**第一站：Spec Coding（2025 年 9 月）**

发现 vibe coding 不够用后，我转向了 Spec-Driven
Development------先写规范再写代码。OpenSpec 的工作流是：写提案 →
生成需求+设计+任务 → 审查 → 按规范执行 → 归档。

Spec Coding 解决了意图对齐的问题。AI
不再猜你想要什么，它有一份明确的合约。代码质量上了一个台阶。但新问题来了------规范写好了，执行还是会断。AI
跑一会儿就偏了、卡了、需要你介入。

**第二站：Superpower 模式（2026 年 1 月）**

我发现一个有效的组合：用 OpenSpec 的 explore 模式让 AI
先探索事实和方法，给我选项让我选方向，然后用 Superpower 的 brainstorm
模式和 AI 一起碰撞方案，最后用 execute plan 模式锁定执行。

关键转变是：从「我写方案让 AI 执行」变成了「AI 探索、我们共创、然后 AI
执行」。我不再是导演，而是合作者。这个组合比纯 spec 有效得多。

**第三站：CodingSys V2-V3（2026 年 3 月）**

核心需求变了------我想让 AI
长时间自主工作，而不是每隔十分钟就需要我介入。于是设计了
CodingSys：守护进程轮询任务、工作区隔离、状态机流转（Todo → Planning →
Executing → Verifying → Done）、指数退避重试、多轮续跑、结构化断点......

系统越来越复杂。为了让 AI
更「可靠」，我加了越来越多的编排逻辑。这是一条看似正确实则危险的路。

**第四站：Garry Tan 的启示（2026 年 4 月）**

然后我读到了 Garry Tan 的「Thin Harness, Fat Skills」，一切豁然开朗。

> *The anti-pattern is a fat harness with thin skills. 40+ tool
> definitions eating half the context window. God-tools with
> 2-to-5-second MCP round-trips. 3x the tokens, 3x the latency, 3x the
> failure rate.*

我做的 CodingSys V3 就是一个典型的 fat harness------用代码控制 AI
的行为，而不是教 AI
自己控制自己的行为。每多一行编排逻辑，就少给模型一分自主空间。

我推翻了 V3、推翻了后来更复杂的 V5，回到了最简的形态：一个 CLAUDE.md
文件 + 五个 slash command + 几个确定性脚本。

**第五站：Agentic 之道**

最终的认知不是某一天突然产生的，而是前面所有弯路的总和。Vibe Coding
教会了信任，Spec Coding 教会了纪律，Superpower 教会了共创，CodingSys
教会了什么该做什么不该做，Garry Tan 教会了做减法。

当这些经验叠加在一起，答案浮出水面------

> *Agentic 之道：不是造更聪明的 AI，而是养更深的 Context。*

**第三章：五条道**

**第一条：信任，然后放手**

2026 年的模型已经足够聪明。Opus 4.6、GPT-5、Gemini
2.5------它们会推理、会综合、会写代码。所有 over-engineering
的根源都是不信任模型。

写状态机是因为不信任模型能判断下一步。写 40 个 tool definitions
是因为不信任模型能用少数工具组合出复杂行为。写详细指令是因为不信任模型能理解你的意图。

但信任不是盲信。Vibe Coding 的盲信（全盘接受、不看代码）和 Agentic
之道的知信（理解能力边界、在关键点做决策）是两回事。知信需要你真正理解模型------什么时候该放手，什么时候该介入。这种判断力不来自理论，来自实战。

**第二条：启发，而非指令**

当下 LLM
已经足够强大，不需要你手把手教它怎么做。它需要的是正确的问题、正确的上下文、和正确的约束边界。

好的 Skill
不是一份操作手册------「第一步做X，第二步做Y」。而是一个思维框架------「先探究事实，再挑战假设，最后收敛方案」。好的
Prompt 不是详细指令，而是好的问题。

这是一个深刻的范式转移。旧范式里，人类是导演，AI
是演员，剧本越详细表演越好。新范式里，人类是提问者，AI
是探索者，问题问得越好发现越深。

**第三条：人在决策点，不在执行链**

有效的工作流是这样的：Explore（AI 探索给你选项）→ 你选方向 →
Brainstorm（你和 AI 共创）→ 你审方案 → Execute（AI 自主执行）→
Verify（AI 自我验证）→ Learn（系统自动积累）。

人出现在两个点：选方向和审方案。其余全交给 AI。

人类的稀缺资源是判断力和品味，不是执行力。Garry Tan
每天产出万行代码不是因为他打字快，而是因为他只保留了战略判断。你不需要做得更多，你需要选得更准。

**第四条：积累，而非编排**

守护进程、状态机、指数退避------这些是「编排」。它们让一次执行更可靠，但不会让第二次执行更聪明。

Brain、Knowledge Tree、Dream
Cycle------这些是「积累」。每一次执行都让系统变得更好。

Garry Tan 说得精准：「Every skill you write is a permanent upgrade. It
never degrades. It never forgets. And when the next model drops, every
skill instantly gets better.」你写的每一个 skill
都是系统的永久升级。它不会退化，不会遗忘。当下一代模型发布时，所有 skill
瞬间变强。

比起跑得快，跑得远更重要。

**第五条：人做减法，AI 做加法**

从 V3 到 V4 到 V5 再到最终版，每一轮迭代都在做减法。最终的系统极简到一个
CLAUDE.md 文件。不是因为功能少，而是因为把复杂度交给了模型。

Harness 薄------只做循环、读写、路由、安全。Skill
薄------启发而非指令。Spec 薄------方向而非详细需求。唯一 fat
的东西是知识（Brain）和确定性工具（Code）。

这就是 Garry 说的三层分离：把智能模糊操作推入 markdown skills（Fat
Skills），把必须完美的确定性操作推入代码（Fat Code），Harness
保持精简（Thin Harness）。

**第四章：五步闭环**

道是认知，术是行动。五条道对应一个极简的五步工作流：

**Step 1：Explore（发现）**

来自 OpenSpec。不告诉 LLM
答案是什么，而是让它自己去探究------扫代码库、查事实、发现约束、理解现状。你只给方向，它给你选项。

Explore 阶段最重要的是：让 AI 自己决定需要什么
context，而不是你一股脑全塞进去。Context 越多不一定越好，精准的 context
才是好 context。OpenAI 的 Harness Engineering 发现，context window 超过
40% 性能反而下降。

**Step 2：Brainstorm（共创）**

来自 Superpower。不是你写方案让 AI 执行，而是你和 AI
一起头脑风暴。它提方案你挑战，你提想法它验证，来回碰撞直到方案成型。

Vibe Coding
的「跟着感觉走」在这里并没有消失------它变成了共创阶段的态度。发散时大胆，收敛时严谨。

**Step 3：Plan（锁定）**

Brainstorm 的产物变成可执行计划。这里吸收了 gstack
的多视角审视模式：不是一个 agent 出计划，而是用 CEO
视角看战略合理性、Eng 视角看架构、QA 视角看验证方案、Security
视角看攻击面。

多视角不是多
agent。是同一个模型戴不同的帽子，确保不遗漏盲区。审视完毕后锁定方案。Spec
Coding 的纪律在这一步。

**Step 4：Execute（执行）**

按计划自主执行。从 Harness Engineering
学到的关键护栏：分层上下文（不塞满 context window）、确定性护栏（lint 和
test 做硬约束，不靠 LLM 自觉）、持久化记忆（progress.json 做断点，用
JSON 不用 Markdown，因为 agent
不太会随意修改结构化数据）、遇阻停止（被阻塞时记录并停止，不乱猜）。

注意：这里不做编排。不写状态机，不做指数退避，不控制并发。这些全交给模型自己判断。你只提供护栏，不提供路线图。

**Step 5：Verify → Learn（验证 → 积累）**

让 agent 自己验证自己的工作------跑测试、看
CI、检查是否满足验收标准。失败了自己诊断原因，而不是机械重试。

然后是最关键的一步------Learn。新决策写入 brain/decisions/，新教训写入
brain/failures/，新 pattern 写入 brain/patterns/，skill
覆盖缺口更新到知识树。

每次执行都让系统变得更聪明。这是复利的来源。也是 Vibe Coding
永远做不到的事。

**第五章：Context 是唯一的护城河**

聊了这么多方法论、框架、工具，最终收敛到一个认知：

> *模型会趋同，工具会趋同，harness 会趋同。唯一不会趋同的是 Context。*

**四层竞争模型**

  ---------------- --------------------- ---------------- ----------------
  **层级**         **内容**              **可复制性**     **护城河**

  **第一层**       模型（Opus/GPT-5）    完全趋同         无

  **第二层**       工具/Harness          已开源           无

  **第三层**       Skills                可自动挖掘       弱

  **第四层**       Context               不可复制         **极强**
  ---------------- --------------------- ---------------- ----------------

越往上越容易被替代，越往下越不可替代。Agentic 的终极竞争在最底层。

**对个人：决策品味的外化**

品味是什么？品味是你在十年实战中积累的、无法用规则表达的判断力------「这个架构闻起来不对」「这个产品方向有感觉」「这段代码虽然能跑但不够优雅」。这些东西传统上只存在于你的大脑里，每次开新
session 都丢失。

把品味持久化到 Brain 里------不是写成规则（那又变成
over-instruct），而是让 AI 通过你的决策历史、偏好
pattern、失败教训「浸泡式」理解你。当 AI 足够理解你的品味时，Explore
阶段它给你的选项就不是通用方案，而是你会选的那类方案。对齐成本趋近于零。这才是真正的
10x。

**对企业：组织记忆的永生**

企业最大的浪费是什么？每次有人离职，他脑子里的 context
就清零了。新人要花三到六个月「重建上下文」------读代码、踩旧坑、问老人。

如果企业的 Brain 是活的呢？每个架构决策都有 compiled truth（当前理解）和
timeline（决策过程）。每个失败记录在案------不是作为 blame
而是作为知识。每个成功 pattern 可检索。

新人入职第一天，AI
已经「懂」这个组织了。不是懂规章制度（那是死文档），而是懂这个团队怎么思考、怎么决策、怎么踩坑又怎么爬出来的。这就是历史的沉淀。

**为什么 Garry Tan 开源工具但不开源内容**

gstack（harness + skills）全部开源，MIT 协议，拿去用。GBrain
的代码也开源了。但他的 10,000 个 markdown
文件------人物页面、会议记录、决策过程、原创思考------不会开源。

因为工具是手段，Context 是资产。他开源的是「怎么建 brain」，不是「我的
brain 里有什么」。

**第六章：Vibe Coding 之道 vs Agentic 之道**

它们不是对立的。Agentic 之道是 Vibe Coding 之道的进化。

  --------------- -------------------------- -----------------------------
  **维度**        **Vibe Coding 之道**       **Agentic 之道**

  **核心假设**    模型够聪明                 模型够聪明，但不够懂你

  **信任方式**    盲信（全盘接受）           知信（理解边界后放手）

  **交互模式**    单向：我说你做             双向：共创

  **状态**        无状态：每次从零           有状态：持续积累

  **规范**        无：跟着感觉走             轻：启发而非指令

  **品味**        不需要（全盘接受）         核心（策展 Context）

  **增长曲线**    线性                       复利

  **适用场景**    原型、验证、一次性         产品、长期、可持续

  **隐喻**        对着许愿机说话             跟越来越懂你的搭档共事
  --------------- -------------------------- -----------------------------

Vibe Coding 的「跟着感觉走」在 Agentic 之道里并没有消失------它变成了
Explore 和 Brainstorm 阶段的态度。Spec Coding
的「先写规范再写代码」也没有消失------它变成了 Plan 阶段的纪律。

真正新增的是两样东西：共创和积累。共创让方案从「你想到的」变成「你们碰撞出的」。积累让系统从「这次好使」变成「每次更好使」。

Vibe Coding 教你敢用 AI。Agentic 之道教你会养
AI。前者是起点，后者是长路。

**第七章：最佳实践与反思**

**Context Engineering \> Prompt Engineering**

2026 年，prompt engineering 已经进化成了 context
engineering------设计的不是一句 prompt，而是 LLM
周围的整个信息环境。Context
不只是喂进去的内容，还包括什么时候喂、喂多少、以什么顺序喂。

Garry 的 Resolver（任务类型→加载哪些 brain page）就是 context
路由。不是一股脑全塞，而是精准地匹配。你的 Explore 阶段让 AI
自己发现需要什么 context，而不是人工决定------这比手动 context
engineering 更优雅。

**Trust 是分级的**

高信任区：探索、头脑风暴、写文档------让 AI
完全自主。中信任区：写核心业务逻辑、改数据库 schema------AI 执行但你
review。低信任区：涉及资金、用户数据、不可逆操作------人类亲自确认。

你的五步流程里，前两步是高信任（AI 自由发挥），Plan
是中信任（多视角审视），Execute 回到高信任但有护栏，Verify
做兜底。这个节奏感已经隐含了信任分级。

**Skill 会老化**

GitHub Copilot 的部署经验告诉我们：prompt 和 tool 老化很快。今天好使的
skill，三个月后模型升级了、API 变了、依赖更新了------可能就失效了。

不需要重型的验证框架，但至少做一个极简的健康检查：每月跑一遍 smoke
test，失效的标记为「需更新」。SkillFoundry
论文的三层验证思路值得借鉴------Execution Testing（能不能跑通）、System
Testing（基础设施验证）、Synthetic Testing（受控输入测试）。

**Single Agent First**

多 agent 编排听起来很酷，但几乎所有成功案例都是单 agent
做透一件事。gstack 的 30+ slash commands 本质上不是 30 个
agent，而是一个 agent 戴不同帽子。先让一个 agent 把 Explore → Brainstorm
→ Plan → Execute → Verify 跑通，再考虑分拆。

**安全不是事后补丁**

Agent 每周写 1,000 个 PR，1% 的漏洞率意味着每周 10
个新漏洞。手动安全审查跟不上速度。解决方案不是加一堆安全工具，而是在
Plan
阶段加一个安全视角------「这个方案有什么可以被利用的攻击面？」一个问题就够了。

**从 Creator 到 Curator**

2026 年的工程师角色正在从 Creator（创造者）变成
Curator（策展者）。你不再是写代码的人，而是选什么进入系统、保留什么、淘汰什么、放大什么信号、抑制什么噪音的人。

把 24 个 skill 精简到 19 个，是策展。在 Explore 阶段选方向，是策展。审
Plan 时决定保留哪些专家意见，是策展。策展能力 = 品味 + 判断力 +
context。这三样东西加在一起，就是人类在 Agentic 时代不可替代的原因。

**第八章：极简实现**

所有这些理念最终收敛到一个极简的实现：不需要框架、守护进程、状态机。一个
CLAUDE.md 文件搞定。

**完整的 CLAUDE.md**

**\## 哲学**

> 你足够聪明。我不会给你详细指令。我会启发你探索，你会启发我决策。我们是共创关系，不是主仆关系。

**\## 工作流**

> /explore --- 探索问题空间，给我发现和选项
>
> /brainstorm --- 和我一起头脑风暴，碰撞方案
>
> /plan --- 锁定方案，多视角审视后输出可执行计划
>
> /execute --- 按计划自主执行，遇阻停止不猜
>

**终章：道**

回到最初的问题------什么是 Agentic 之道？

说到底，三个字：养 Context。

其他所有东西------模型选择、harness 设计、skill 写法、多 agent
编排、OpenSpec、Superpower------都是手段。目的只有一个：让你的 AI
越来越懂你。

模型是公共品，人人都能用。工具是开源的，Garry 都送你了。Skill
可以自动挖掘，SkillFoundry
证明了。唯一不可复制的，是你喂养了多久、喂养了什么、用什么品味在策展你的
context。

往深了说，Agentic 之道其实跟中国人讲的「道」是一回事：

> 道生一------一个足够好的 context。
>
> 一生二------分化为个人品味和组织记忆。
>
> 二生三------品味 + 记忆 + 模型智能，三者交汇。
>
> 三生万物------系统自演进，越用越强，每次交互都是积累。

你不是在「使用」AI。你是在养一个越来越懂你的东西。就像养龙虾------环境对了，它自己会长。

**Vibe Coding 之道说：忘记代码，拥抱 AI。**

**Agentic 之道说：忘记指令，养好 Context。**

**前者教你信任。后者教你如何让信任越来越值钱。**

**这件事没有捷径，但有复利。**
