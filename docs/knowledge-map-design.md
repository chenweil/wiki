# MyWiki Knowledge Map Design

这份文档记录 MyWiki 知识地图的已确认设计。知识地图的第一性目标是知识导航与发现：用户从一个已知页面出发，发现原本不知道但相关的页面，查看关系依据，并在 2～3 次交互内打开目标 Wiki 页面。

本设计来自用户确认的 grilling session，以及对 Hermes Studio“学习轨迹”页面交互的观察。Hermes Studio 只作为交互参考，不是 MyWiki 的运行时依赖或集成目标。

## 1. 边界与事实来源

- `wiki/` 中已维护的页面是地图的输入。
- Wiki 页面、原始来源、引用和页面关系仍然是唯一事实来源。
- 地图是可重建的只读投影，不是第二套知识库。
- 地图第一版通过独立的本地地图查看器使用，不接入 Hermes Studio。
- 地图生成只在用户显式刷新或一次明确的 ingest 流程之后发生。
- 地图不会自动扫描整个 Obsidian vault、IMA 或 `raw/`。

详细架构决策见 [`ADR-0001`](adr/0001-knowledge-map-as-rebuildable-projection.md)。

## 2. 第一版范围

第一版只构建 AI 工程主题子图，覆盖当前已维护的 Claude Code、Agent、Skill、Plugin、Agent Harness 和 Loop Design 相关页面。

第一版暂不覆盖：

- 哲学类页面；
- Go 学习路线；
- `wiki/index.md`、`wiki/log.md` 等操作页；
- 来源摘要或正文不完整的页面作为正常语义节点；
- Hermes Studio 集成；
- 时间回放和实时学习轨迹；
- 面向无限规模全 Wiki 的性能承诺。

随着节点数量增长，地图通过主题聚类和分层展开控制复杂度，而不是无限增加关系线。

## 3. 领域模型

### 知识节点

一个已经进入 `wiki/` 知识层并具有自身页面的 source、concept 或 synthesis。原始材料、外部来源实例、临时文件和标签不是第一版地图中的节点。

### 显式关系

由页面中的 `[[wikilinks]]` 或 `sources` 依赖直接表达的关系。它代表已有的知识证据，默认完整保留并使用更强的视觉样式。

### 推断关系

由 embedding 语义相似度或其他派生分析得到的关联。它只用于探索提示，不等同于 Wiki 已确认的事实关系。每条推断关系都必须展示关系依据，例如语义相似、共享主题标签、共享来源或相近概念。

### 主题标签

用于分类、筛选和聚类的节点属性。标签不自动生成地图关系线。

### 未定位节点

已经纳入主题子图，但没有成功获得语义坐标的节点。它仍然可见并保留可用的显式关系，同时在地图和生成报告中说明缺失或失败原因。

## 4. 语义空间与关系叠加

- embedding 决定页面在语义空间中的相对位置。
- `[[wikilinks]]` 和 `sources` 作为关系叠加层绘制在语义空间之上。
- 显式关系不强行修改 embedding 坐标。
- 推断关系从语义邻近结果中产生，但必须受关系预算限制。
- 同一输入、embedding 后端、降维算法、参数和随机种子下，节点位置应稳定。
- 数据或模型变化导致的重新布局属于新的地图版本。

关系预算的默认规则：

1. 显式关系全部保留；
2. 每个节点默认最多展示 3 条推断关系；
3. 其余推断关系通过“展开更多”查看；
4. 不生成无阈值的全连接图。

## 5. Embedding 输入与隐私

embedding 只读取纳入第一版主题子图的 Wiki 页面维护内容：标题、摘要、关键点、标签和正文。原始 Obsidian、IMA 和 `raw/` 内容不直接进入向量化流程。

embedding 后端是可替换的生成实现。具体后端、模型、版本、参数和输入 hash 必须记录在地图 manifest 中，但不属于 Wiki 的领域事实。

- 本地 embedding 可以作为默认运行方式；
- 远程 embedding 必须由用户显式 opt-in；
- 默认不把 Wiki 内容发送到外部服务；
- 远程请求失败时，页面保留为未定位节点，不自动切换到未知服务；
- manifest 记录服务和模型信息，不保存完整页面文本。

## 6. 视图与交互

### 默认导航视图

2D 视图是默认入口，优先保证节点定位、关系阅读、筛选和可访问性。

### 探索视图

3D 视图是可选入口，用于观察整体语义分布和发现远近关系。3D 坐标是派生展示，不是可解释的三条事实维度，也不改变节点和关系语义。

### 视觉编码

- 颜色表示主题；
- 形状表示页面类型：source、concept、synthesis；
- 第一版不使用节点大小表达重要性；
- 选中节点使用高亮环或其他明确的选中状态；
- 显式关系使用更强样式，推断关系使用较弱样式，并标记关系类型。

### 节点详情

单击节点打开详情面板，地图保持当前位置。详情面板展示：

- 标题和页面类型；
- 摘要、标签和更新时间；
- 来源；
- 显式关系；
- 推断关系及关系依据；
- 未定位或生成失败原因（如适用）；
- 打开原始 Wiki 页面的动作。

地图是只读的。用户不能在地图里修改标题、摘要、标签、来源或关系；所有编辑回到 Wiki 页面完成。

### 搜索与列表

搜索或节点列表与地图是两个平等入口：

- 搜索标题、标签和摘要；
- 从列表选中节点，地图定位并打开详情；
- 从地图选中节点，列表同步高亮；
- 键盘可以在列表和详情面板中完成导航；
- 3D 不是唯一的访问方式。

### 筛选

默认使用聚焦模式：保留全局结构，只降低不匹配节点和关系的透明度。另提供严格隐藏模式，但隐藏不代表节点不存在。

## 7. 派生数据与生成生命周期

坐标、embedding、推断关系和地图 manifest 都是可删除、可重新生成的派生地图数据，不允许手工编辑，也不作为 Wiki 的主数据。

manifest 至少记录：

- 页面 slug 和页面内容 hash；
- 地图主题范围；
- embedding 后端、模型和版本；
- 降维算法、参数和随机种子；
- 地图版本和生成时间；
- 节点状态，包括已定位和未定位；
- 推断关系及关系依据。

生成失败的页面不能静默丢弃。地图应保留其节点清单状态，继续展示可用的显式关系，并在生成报告中说明原因。生成过程不能修改 Wiki、原始来源或外部 Obsidian vault。

## 8. 第一版验收

第一版不先设复杂的模型 KPI，而使用固定导航验收场景：

1. 从一个已知 AI 工程页面出发；
2. 发现至少一个原本不知道但相关的页面；
3. 查看该关系的依据，并明确它是显式关系还是推断关系；
4. 在 2～3 次交互内打开目标 Wiki 页面；
5. 显式关系没有丢失；
6. 未定位节点没有被静默丢弃；
7. 相同输入下节点位置保持稳定；
8. 刷新和查看过程不修改 Wiki 或外部来源；
9. 搜索/列表入口能够完成同一节点的定位和跳转。

## 9. 延后决策

以下内容尚未锁定，不应在实现阶段被偷偷当成既定事实：

- 具体 embedding 模型和默认后端；
- 降维算法及 2D/3D 渲染技术；
- 派生 artifact 的具体目录和文件格式；
- 页面 slug 到本地 Wiki 文件的链接方式；
- 主题标签的来源和人工/自动分类规则；
- 主题聚类的触发阈值和分层交互。

这些是下一阶段实现 POC 时需要单独验证的技术决策，不改变当前领域边界。

## 10. POC 交互选择

对三个 throwaway UI 变体进行比较后，用户选择 **B · List-first Navigator** 作为后续实现的首选交互结构。

B 版的核心信息层级是：

1. 左侧节点列表/搜索，用于定位已知页面；
2. 中间地图，用于观察语义邻近和显式关系；
3. 右侧详情，用于查看关系类型、推断依据和 Wiki 跳转。

A 版和 C 版保留为设计对照，不构成生产实现。后续真正实现时，应重新编写 B 版的生产代码，而不是直接把 throwaway 原型提升为正式界面。

## 11. Graph Query 与 Provenance 增补

本增补借鉴 [WeKnora 官方仓库](https://github.com/Tencent/WeKnora)公开实现中的两类模式：把 Wiki 页面链接图与实体/语义关系图分开，以及通过有边界的 subgraph 查询支持大图交互。WeKnora 的引用抽屉、稳定资源标识和 citation tracing 也提供了 provenance 交互的参考。借鉴这些模式不等于引入 WeKnora 的数据入口、图数据库、RAG、Agent 或运行时。

### 11.1 两个关系层

地图数据继续使用同一套知识节点，但关系必须分为两个可独立查询和筛选的层：

- **页面链接图**：由 `[[wikilinks]]`、`sources` 等 Wiki 明确声明产生。它代表已有知识证据，显式关系默认完整保留。
- **语义探索图**：由 embedding 或其他派生分析产生。它只用于发现潜在相邻页面，默认受关系预算限制，并必须展示关系依据。

两层可以在 B 版地图中叠加显示，但不能在数据合同、视觉编码或详情说明中混成同一种关系。第一版不新增独立的实体自动抽取图。

### 11.2 快照、查询和子图结果

地图不再假设查看器每次都加载完整图谱，而是围绕一个不可变的地图快照提供只读查询：

- **地图快照**记录地图版本、主题范围、输入页面 hash、embedding/投影配置、节点状态和关系数据；它仍然是可删除、可重建的派生数据。
- **图谱查询**至少表达起点节点、关系层、展开深度或范围、关系预算、筛选条件和继续展开所需的游标/句柄。
- **子图结果**返回有限节点和关系、被省略数量、继续展开信息、部分失败状态以及对应的地图快照版本。

B 版查看器的加载行为调整为：列表/搜索定位节点，地图先加载该节点的有限邻域；用户按关系层或“展开更多”请求后续子图。查询不得修改快照，也不得静默把局部结果伪装成完整地图。

### 11.3 结构化 provenance

provenance 从详情里的说明文字提升为派生数据合同的一部分：

- 节点回溯到 Wiki 页面身份、页面内容 hash 和生成运行；
- 显式关系回溯到来源页面、字段或关系声明，以及目标页面；
- 推断关系记录 embedding 后端、模型/版本、输入 hash、生成配置和关系依据，而不是只保存一个不可解释分数；
- 一次子图结果记录地图快照版本、查询条件和结果是否完整、截断或部分失败；
- manifest 和 provenance 默认不保存完整原始文本，不扩大 MyWiki 的来源边界。

详情面板应能让用户回答三个问题：这个节点来自哪里、这条边为何存在、当前看到的子图属于哪个地图版本和查询范围。

### 11.4 第一版验收增补

在原有导航场景之上，第一版还需要验证：

1. 从已知节点进入时只加载有边界的初始子图，并明确其范围；
2. 用户可以继续展开邻域，且展开不会改变已确认节点和关系的身份；
3. 页面链接图和语义探索图可以独立筛选、计数和解释；
4. 节点、显式关系、推断关系和子图结果都能展示对应 provenance；
5. 结果被限制、部分失败或无法定位时，界面显示省略数量、继续展开方式或失败原因；
6. 同一个地图快照和同一个图谱查询得到稳定的节点位置与关系集合；
7. 查询、展开和查看过程不修改 Wiki、来源台账、`raw/`、Obsidian 或 IMA；
8. 查询深度可以向下收起，并能将 depth 与关系预算重置为默认查询，不需要刷新页面。

具体 API 传输方式、artifact 是否分片、游标格式、本地索引实现和 3D 渲染方式继续延后决定。详细边界见 [`ADR-0002`](adr/0002-queryable-subgraphs-and-structured-provenance.md)。
